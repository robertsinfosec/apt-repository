## Source and Build Separation
This project separates source from generated output to keep the APT repository and documentation maintainable. All implementation code, configuration, and scripts live under `src/`, while `docs/` contains human-readable design notes like this file. The `dist/` directory is reserved for build artifacts and will be regenerated by scripts or CI, meaning it should remain free of hand edits. This separation makes it clear where contributors should make changes and what can be safely deleted and rebuilt. It also ensures deployments can mirror the exact contents of `dist/` without hidden state.

## Role of src/apt/
The `src/apt/` tree will hold everything needed to construct the Debian-style repository served to `apt`. Configuration for tools such as reprepro will live in `src/apt/conf/`, while scripts under `src/apt/scripts/` will transform `.deb` inputs into `dist/dists/` and `dist/pool/`. These scripts are expected to operate on one or more package artifacts, including the initial `compose-upgrade` package, without hard-coding specific package names. Future CI jobs will call these scripts to refresh metadata, place packages, and handle signing as required. Local developers should be able to run the same scripts inside the dev container to reproduce the `dist/` tree for testing.

## Role of src/docs-site/
The `src/docs-site/` directory will contain the static site generator source that produces the documentation hosted at `/docs`. Its build output will be written to `dist/docs/`, alongside supporting root files like `dist/robots.txt` and `dist/sitemap.xml` that guide crawlers. The docs site will describe how to add the repository, list available packages, and provide per-tool guides such as for `compose-upgrade`. Keeping the source here allows iterative improvement to the docs without touching generated files. The build process should remain deterministic so the same source inputs always yield the same deployable site in `dist/docs/`.

## Tool Sources and Packaging
This repository is a monorepo that can hold the source code and packaging metadata for multiple administrative tools. Each tool should live under a dedicated path such as `src/tools/compose-upgrade/`, keeping its executable, man page, and packaging scripts together. Debian packages are built from these directories into an artifacts location, then consumed by the APT build scripts to populate `dist/dists/` and `dist/pool/`. This approach keeps tool evolution, packaging, and repository publishing in one place without scattering submodules. The resulting `.deb` files remain inputs to the APT build even though their source is co-located.

## Stage 1: Tool Build
Each tool is authored under `src/tools/{tool-name}/`, keeping source code, manual pages, and packaging files side by side. The build process for a tool produces Debian packages into `artifacts/{tool-name}/`, ensuring outputs never mix across tools. Tool builds are responsible for setting correct metadata, versioning, and install paths so downstream consumers treat them as ready-made inputs. Because this stage is isolated per tool, multiple packages can evolve independently while sharing the repository infrastructure. The pipeline assumes a clean dev container or runner provides standard Debian packaging utilities like debhelper and dpkg-buildpackage.

## Stage 2: APT Repo Assembly
All `.deb` outputs from `artifacts/*/` are fed into the APT assembly scripts under `src/apt/scripts/`, which use configuration from `src/apt/conf/`. The assembly step generates `dist/dists/` and `dist/pool/`, indexing every provided package without hard-coding names so new tools can be added freely. It may also sign Release metadata when provided a key, and it always refreshes metadata to match the current artifact set. The process is deterministic: the same set of inputs yields the same repository layout, allowing CI and local runs to match. Strong validation ensures the dist tree contains expected Release files, package pools, and crawl directives before deployment.

## Stage 3: Docs Build
The documentation source under `src/docs-site/` produces the static site emitted into `dist/docs/`, alongside crawler guidance in `dist/robots.txt` and `dist/sitemap.xml`. This stage explains how to add the repository, lists available packages, and links to per-tool guides so browser visitors can understand and trust the APT repo. The docs build is isolated from the APT assembly so it can iterate quickly without altering package metadata. Outputs are fully static and ready for hosting at `https://apt.robertsinfosec.com/docs/`, matching the deployable structure in `dist/`. Because the docs live under `src/`, rebuilding them never risks hand-editing generated assets.
